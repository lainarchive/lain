# 01 — Event Store Specification (M-1's central subsystem)

**Status:** Proposed specification, implementation-ready. **Nothing here is implemented or accepted.**
**Base revision:** `36a3e18003ad41171be96d28cfbbda5b5304441c`
**Labels:** EUR · EAD · ESR · UAP · OQ · HIST · SESS
**Scope:** the complete design of Lain's append-only event store: data model, write and read guarantees, security, recovery, operations, storage tradeoffs, and exactly what is achievable on Windows.

---

## 0. Why this subsystem is first

**ESR.** Every other capability in Lain records what it did through this store. The audit's most blocking canonical gap is that the event log has **no owner** and "single-writer" appears **zero times** in the repository, while the only measurement available shows what its absence costs: with per-document commits, **963 torn reads in 1 766 observations**; with one transaction per batch, **0 torn reads in 1 212** (HIST, `.lain-audit/20-p0-preparation.md` §4, E-3). The store is therefore both the first thing to build and the thing that makes every later claim checkable.

**EAD.** ADR-003 (Core owns canonical state) and ADR-007 (SQLite + FTS5, *Proposed*) frame the choice; ADR-005 (unknown cost fails closed) and ADR-004 (authorization external to prompts) frame the security posture. ADR-007 remains **Proposed** — this document does not promote it.

## 1. Data model

### 1.1 Event record (ESR — UAP until adopted)

| Field | Type | Required | Notes |
|---|---|---|---|
| `event_id` | ULID (26 chars, Crockford base32) | yes | **Monotonic within a store**, lexicographically sortable, generated by the writer. Chosen over UUIDv4 because ordering is a first-class requirement and over an integer sequence because IDs must be usable as a durable external reference before commit. |
| `seq` | INTEGER PRIMARY KEY AUTOINCREMENT | yes | Store-assigned total order. The **only** authority on order; `event_id` is a tie-break aid, never the ordering key. |
| `event_type` | TEXT, dotted namespace (`task.created`, `policy.decided`, `tool.executed`) | yes | Validated against a compiled-in registry; unknown type is rejected at the store boundary, not silently stored (fail-closed, EUR). |
| `schema_version` | INTEGER | yes | The payload schema version for that `event_type`. The store refuses to write a version it does not know. |
| `occurred_at` | TEXT, RFC 3339 with offset, milliseconds | yes | When the *producer* says it happened. |
| `recorded_at` | TEXT, derived by the store | yes | When the store accepted it. **Never supplied by a caller** — this is what makes clock skew visible rather than hidden. |
| `session_id` | TEXT, nullable | no | Foreign reference to a session record. |
| `task_id` | TEXT, nullable | no | Foreign reference to a task record. |
| `producer` | TEXT (`component@version`, e.g. `policy@0.1.0`) | yes | Who wrote it. Free-text self-identification is **not** an authorization input (EAD, ADR-004). |
| `correlation_id` | TEXT, nullable | no | Groups events belonging to one user request or objective. |
| `causation_id` | TEXT, nullable | no | The `event_id` that directly caused this event. Enables causal chains without a separate graph store. |
| `payload` | TEXT (JSON) or NULL | no | **After redaction** (§5.1). Stored as text, not a JSON column type, so the store never re-serializes and cannot silently change bytes. |
| `payload_digest` | TEXT, SHA-256 of the stored payload bytes | conditional | Present iff `payload` is non-null. Detects corruption and makes tamper-evidence possible. |
| `redaction` | TEXT, nullable JSON | no | What was removed and why: `{"applied":["email","api_key"],"rule_version":1,"reason":"store-level-policy"}`. **The fact of redaction is itself recorded** — a silently altered payload is worse than a rejected one. |
| `provenance` | TEXT, nullable JSON | no | Producer-declared source: `{"kind":"model","binding":"qwen3-4b@sha256:1a2c…","run_id":"…"}` or `{"kind":"user","input_event":"…"}`. |
| `schema_ok` | INTEGER 0/1 | yes | 1 when the payload validated against its registered schema at write time. A 0 row is stored **only** for forensic continuity of an already-committed batch and is never returned by default reads. |

### 1.2 Indexes (ESR)

`seq` (primary) · `(event_type, seq)` · `(session_id, seq)` · `(task_id, seq)` · `(correlation_id, seq)` · `(occurred_at)`. **No index on `payload`** — full-text search is a later, optional subsystem (FTS5 via ADR-007) and must not be implied by this schema. Budget arithmetic from the audit (**HIST**): **146 B/event** at 100 000 rows with WAL and batch commits, **143–147 B/event** across the measured variants; therefore **1 M events ≈ 146 MB**, which is affordable, and **1 M events with FTS5 is not measured** (see `03-resource-budget-specification.md` §6, measurement P-2).

## 2. Write guarantees

### 2.1 Single writer (ESR — the core guarantee)

- **One writer process per store file at a time**, enforced by two independent mechanisms: (a) an **exclusive OS file lock** on a sibling `store.lock` held for the writer's lifetime, and (b) SQLite's own write lock within a transaction. The second is a backstop against a second writer that bypasses the first; a second writer must fail **loudly and immediately** with a distinguishable error, never by blocking silently.
- **The lock is advisory across processes only for writers.** Readers never take the lock (§3).
- **Liveness:** the lock file carries `{pid, boot_id, acquired_at, hostname}`. A stale lock (PID not alive, or `boot_id` differs) may be reclaimed, and **the reclamation is recorded as an event on next open** so that a double-writer episode is never invisible.

### 2.2 Transaction boundaries and batch semantics (ESR)

- The unit of atomicity is a **batch**: 1..N events plus their schema validations, committed in **exactly one transaction**. This is the measured decision (**HIST**: one transaction per batch = 0 torn reads in 1 212; per-document commits = 963 torn in 1 766) and is stated by the first-vertical-slice research as "a correctness requirement, not an optimisation".
- **Batch-level properties:** all events in a batch are contiguous in `seq`; a batch never interleaves with another batch (single writer); a failed batch leaves **no** row behind.
- **`journal_mode=WAL`, `synchronous=FULL`** for the store's own durability, with the caveat that `FULL` on Windows is bounded by what the OS and the drive cache actually guarantee (§8). `NORMAL` is a **configuration choice with a recorded reason**, never a silent default, because it trades durability for throughput and the trade must be visible.
- **fsync policy:** SQLite performs its own; the store additionally fsyncs nothing itself (double-fsync adds cost without adding a guarantee SQLite has not already given).

### 2.3 Ordering, idempotency, duplicates (ESR)

- **Ordering is `seq`.** Producers must not assume wall-clock ordering; `occurred_at` can go backwards (clock adjustment, concurrent producers) and the store does not reject it — it records `recorded_at` so the skew is observable.
- **Idempotency key:** an optional `idempotency_key` column with a **UNIQUE index scoped to `(producer, event_type, idempotency_key)`**. A duplicate insert returns the **existing** `event_id` and `seq` with a `duplicate=true` result rather than raising — because a retried operation after an unknown outcome is a normal condition (Phase 5 effect classes), not an error.
- **Duplicate handling rule (ESR):** the store never silently drops an event. Either it is a recognized replay (idempotency match → return the original) or it is stored. "Deduplicate by content" is explicitly rejected: two identical-looking events can be two real events.

### 2.4 Durable acknowledgement (ESR)

An append call returns only after `COMMIT` has succeeded. The returned receipt carries `{batch_id, first_seq, last_seq, count, committed_at, duplicates[]}`. **A caller that has not received a receipt must treat the write as indeterminate** — this mirrors the approval semantics (`DenyIndeterminate`) and is what makes crash recovery honest (§6).

## 3. Read guarantees

- **Concurrent readers are unlimited** and never block the writer (WAL). A reader sees a **consistent snapshot** for the duration of its read transaction.
- **Ordering:** reads are ordered by `seq` unless a caller explicitly requests `occurred_at` ordering, in which case the response carries a flag saying so.
- **Pagination:** keyset pagination on `seq` (`after_seq`, `limit`), never `OFFSET` — offset paging degrades and can skip or repeat rows under concurrent writes.
- **Filtering:** by `event_type`, `session_id`, `task_id`, `correlation_id`, `occurred_at` range, and `schema_ok`. Any filter compiles to an indexed query; an unindexed filter is refused rather than served slowly (a silent full scan on a growing log is how a responsive system becomes an unresponsive one).
- **Retention:** **nothing is deleted by default.** Compaction/retention is a separate, explicitly-configured subsystem that must preserve `seq` continuity by writing tombstone events, never by deleting rows in place. **Rationale (ESR):** the store's value is that it can prove what happened; a log that silently forgets cannot.
- **Integrity verification:** a `verify` operation recomputes `payload_digest` for a `seq` range and reports mismatches; it also runs `PRAGMA integrity_check` and a foreign-key check. Verification is **read-only** and safe to run at any time.

## 4. Storage-approach comparison (ESR)

| Approach | Dependency cost | Windows reality | Single-writer story | Verdict |
|---|---|---|---|---|
| **`node:sqlite` (Node 24 built-in)** | **zero** — ships with the runtime; `node v24.21.0` is present (SESS) | uses the bundled SQLite; file locking is Windows-native via the OS | needs the explicit lock file (§2.1) because SQLite's own locking is per-transaction | **Recommended for M-1** |
| `better-sqlite3` (native addon) | one native dependency, prebuilds, ABI churn on Node upgrades | works; prebuild availability is the risk | same as above | Rejected for M-1: adds a dependency for synchronous convenience the built-in already provides |
| JSONL append-only file + own fsync | zero | append is not atomic on Windows without `FILE_APPEND_DATA` discipline; no transactional multi-record batch | trivially single-writer by file lock | Rejected: **the batch atomicity requirement (§2.2) is exactly what it cannot give**, and that requirement is the measured one |
| External database service (Postgres et al.) | a service to install, run, secure and back up | needs elevation to install a service | strong | Rejected: permanent constraint 7 (modular without distributed complexity) and $0 |
| Event-sourcing library / message broker | large dependency surface | varies | varies | Rejected: constraint 6 (minimal dependencies); the store is ~600 lines of code, and an unread dependency in the most security-relevant component is a liability |

**Why `node:sqlite` (ESR).** It satisfies all five hard constraints at once: $0, zero added dependencies, local-first, Windows-native, and small enough to read in full. Its main limitation — a synchronous API — is **not a limitation here**, because a single-writer store wants serialized writes anyway, and M-1's throughput requirement is measured in events per second during interactive work, not in tens of thousands.

## 5. Security

### 5.1 Redaction on write (ESR — the guarantee that cannot be retrofitted)

- A **store-level redaction filter** runs on the payload **before** the row is inserted, using a versioned rule set (`rule_version` recorded in the `redaction` column). Rationale (**HIST**, audit E-4): append-only payloads make a secret leaked once **permanent**, and no later store-level redaction can reach it.
- Redaction is **not** a prompt instruction and **not** a caller responsibility: it is the last gate before durability (EUR — security enforced outside the model).
- **Fail-closed rule:** if the filter cannot classify a payload (rule error, timeout, unknown encoding), the write is **refused**, not passed through.
- The filter's own counters (`scanned`, `redacted`, `refused`) are queryable, so AT-8.07's "measured by the store-level redaction filter's own counters" has a real source.
- **Secrets never enter the store in the first place** (Phase 8 §3.3): credential *handles* are recorded, values are resolved at point of use.

### 5.2 Access control and auditability (ESR)

- The store file lives under a directory whose ACL grants the user and denies broad groups; the writer additionally sets a **low-integrity-compatible** posture only when the containment design (§`02-security-and-containment.md`) says the store must be writable from the contained process — **it must not be**. The store is outside the contained workspace (ESR).
- Every append is self-auditing by construction: `producer`, `recorded_at`, `provenance`, `payload_digest`. **The store cannot be used to authorize anything** (EAD, ADR-004) — it is a record, not a policy input.
- **Tamper evidence (ESR, UAP):** each batch records `prev_batch_digest` and its own `batch_digest`, forming a hash chain. This is cheap, detects in-place edits, and does **not** claim to prevent them (an attacker with write access can rebuild the chain — see §8's honesty note).

### 5.3 Path and file protection (ESR)

- The store opens with an **explicit absolute path**, never a lookup, never a path derived from model output. Symlink and reparse-point resolution is performed once at open and the resolved identity is recorded.
- The store refuses to open a path whose resolved location is inside the contained workspace.
- Open flags are least-privilege: read-only mode for verification, no-create for reads, and no shared-write handle.

## 6. Recovery

| Scenario | Design behaviour | Verification |
|---|---|---|
| Interrupted write (process killed mid-batch) | WAL rollback on next open; the batch is **absent**, not partial | AT-M1-06 (kill during batch, assert 0 torn rows) |
| Partial batch in WAL | SQLite rolls back the uncommitted transaction; the store additionally asserts `count == last_seq − first_seq + 1` per batch at open | AT-M1-06, AT-M1-07 |
| Corrupt record | `verify` reports the `seq` and the digest mismatch; the store **refuses to silently skip** — reads that encounter a corrupt row fail loudly with the location | AT-M1-13 |
| Corrupt header / unopenable file | the store refuses to start, names the path, and **does not** recreate an empty store over it | AT-M1-13 |
| Schema migration | forward-only, versioned, in a transaction, with a **pre-migration backup** and a recorded migration event; a failed migration rolls back and leaves the version unchanged | AT-M1-11 |
| Backup | `VACUUM INTO <path>` (a consistent single-file copy) **plus** a recorded event stating that a backup was taken | AT-M1-14 |
| Restore verification | the restore procedure opens the copy, runs `verify`, compares `max(seq)` and a sampled digest set against the source, and reports drift | AT-M1-14 |
| Hash-chain mismatch | reported as a distinct verdict (`CHAIN_BROKEN`), not merged into "corrupt" — the two have different causes | AT-M1-15 |

**ESR — the honest limit.** Recovery can prove *what the store contains*; it cannot prove *what a crashed process intended*. That is why the receipt in §2.4 exists and why the vertical slice's task states include an explicit `indeterminate` outcome.

## 7. Operations

- **Initialization:** `init` creates the file, applies migrations, writes a `store.initialized` event, and prints the resolved path + schema version. It is idempotent.
- **Shutdown:** flush, release the lock, write `store.closed` (best-effort — an ungraceful exit must not be an error condition). A **missing** `store.closed` is itself informative and is reported at next open as `previous_session_ungraceful=true`.
- **Lock acquisition/release:** on start, on shutdown, and on abnormal exit via OS handle release (the lock dies with the process — that is the point of using an OS lock rather than a flag file).
- **Multiple-process contention:** second writer exits with a distinct code and a message naming the holder's PID and start time.
- **Storage exhaustion:** the append fails, returns a distinct `ENOSPC`-class error, and the store remains **openable and readable**. It never truncates to make room.
- **Permission failure:** distinct error, no retry loop, no silent fallback to a temp directory (a silent relocation of the audit log is a security defect, not resilience).

## 8. What is realistically achievable on Windows — stated plainly

**ESR — guarantees the design can make on this platform:**

1. **Batch atomicity** — yes (SQLite transactions + WAL).
2. **Single writer enforced** — yes (OS file lock; second writer fails loudly).
3. **Crash-consistent reopen** — yes (WAL recovery), verified by a kill test.
4. **Detectable in-place tampering** — yes, probabilistically bounded by hash-chain verification, **not** prevention.
5. **Durability across power loss** — **partially.** With `synchronous=FULL`, SQLite fsyncs the WAL, but Windows and the drive's write cache mediate the final guarantee. The honest statement is: *"durable against process crash and OS crash; against sudden power loss, durability is bounded by the storage stack's own flush behaviour, which Lain does not control and does not claim."* A test that pulls power is **not** in the acceptance set because this machine cannot perform it repeatably (AT-M1-08 is marked accordingly).
6. **Confidentiality of the store file at rest** — **no.** The store is plaintext. Encryption at rest is a separate decision (OQ-M1.9) and would need a key-management story that does not exist. Claiming confidentiality without it would be exactly the overstatement the audit flagged in `SECURITY_MODEL.md:42`.

**ESR — guarantees the design explicitly does NOT make:** no protection against an attacker running as the same user with full file access (they can delete, truncate or rewrite the store); no network-facing surface (there is none); no multi-machine replication; no secrecy of payload contents from a process that can read the file; no claim that the event log constitutes a legally meaningful audit trail.
